The core engine that turns a search into a printed result

This directory holds the brain of the program: it reads command-line flags, walks the filesystem looking for matches, and decides how each match gets shown or acted on. Every other piece of the tool, including the parts that filter by size or run a command on each result, is wired together from here.

How a search actually happens

Everything starts in main.rs, where Opts::parse builds the raw command-line options. Those options are shaped by the Opts struct in cli.rs, which declares every flag fd accepts. The struct is intentionally raw and clap-shaped; it is not yet the configuration the rest of the program uses.

main.rs then translates those raw options into a single Config struct that captures every decision the search needs, via construct_config, which resolves case sensitivity, colors, hyperlinks, and the command to run. This is the seam where flags stop being strings and become behavior.

Config and the compiled regex patterns are handed to walk::scan, which spawns a parallel filesystem walker and a receiver that prints or executes results. The walker inspects each DirEntry, a wrapper that lazily loads metadata and style only when needed and applies file-type, size, time, and owner filters before an entry ever reaches the screen.

Matching entries are either printed by print_entry, which colorizes, hyperlinks, and sanitizes each path before writing it, or handed off to the exec module if the user asked for a command to run on every result. filetypes.rs and filesystem.rs supply the low-level predicates, like whether an entry is a socket or an empty file, that the walker consults on every entry.

Seams and sharp edges

Config is the single source of truth

Every downstream module reads from Config rather than re-parsing options. Adding a new flag means adding a matching field to Config and setting it inside construct_config; skipping either half leaves the flag silently inert.

Terminal output is sanitized before it hits your screen

Every printed path passes through maybe_sanitize, which escapes control characters, bidi overrides, and other terminal-injection tricks whenever output is a TTY. Piped output skips sanitization on purpose so raw bytes reach downstream tools intact.

Path separator mistakes look like silent failures

If a user pastes a full path as the search pattern instead of a filename fragment, ensure_search_pattern_is_not_a_path catches the '/' character and raises a clear error instead of returning zero results. Removing this check would turn an obvious user mistake into a confusing empty result set.

Stripped paths must never start with a dash

When the current-directory prefix is stripped from a path, stripped_path checks whether the result would start with a dash and keeps the './' prefix if so, so downstream shells or --exec commands never mistake a filename for a flag.

How the child modules plug into the walk

Filters, formatting, and execution all key off Config

The exec module is only reached when Config carries a command; WorkerState::receive checks config.command and dispatches to exec::batch or exec::job accordingly instead of the default ReceiverBuffer that just prints paths.

The filter module's types live directly on Config: size, time, and owner constraints are checked inline inside the walker's closure that filters each entry by size, time, and ownership before sending it onward. None of these filters know about each other; the walker is what combines them.

The fmt module is invoked only when a --format string is supplied; print_entry checks config.format and calls print_entry_format instead of the colorized or uncolorized paths. Getting this branch wrong means format strings are silently ignored in favor of plain path printing.

Seams and sharp edges

Exit codes always merge to the worst outcome

Whether from parallel exec jobs or the walk itself, merge_exitcodes returns GeneralError if any result was an error, otherwise Success. A single failed command anywhere in a batch run makes the whole invocation report failure.
